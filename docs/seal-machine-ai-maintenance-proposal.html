System Architecture Proposal

通信機能付きシール機（PIC制御）× PC によるAIリアルタイムメンテナンス構成案

現場のインパルスシーラーが持つ通信機能とPICの内部信号を活用し、PC・クラウド上のAIで異常検知と予知保全をリアルタイムに行うための、5層アーキテクチャの提案です。

01提案の全体像

シール機自体は「熱と圧力で溶着する」というシンプルな物理プロセスですが、故障の予兆は電流・温度・時間といった信号の微妙なドリフトとして現れます。これを人手のログ確認ではなくAIに常時監視させ、故障の「前」に知らせる仕組みを作るのが本提案の狙いです。

基本方針は次の3点です。

  • 安全はハードウェア、判断はAI。 過昇温遮断やヒューズなど既存の安全機構はそのまま維持し、AIは「助言・通知」に徹します。AIの誤判定が停止事故につながらない構成にします。
  • PIC側は「測って送る」に専念。 演算負荷の高い異常検知・学習はPC／クラウド側に置き、PICファームウェアの改修は最小限（センサー読み取りとテレメトリ送信）に留めます。
  • 1台のPoCから段階的に拡張。 まずPC1台・シール機1台でしきい値ベースの監視を立ち上げ、データが蓄積してから機械学習モデルへ移行します。

02システム構成図

図: シール機（PIC）→ 通信層 → PCエッジゲートウェイ → クラウド → ダッシュボード/通知の5段構成。破線は助言的フィードバックのみで、機械停止などの安全動作はPIC側ハードウェアで独立に確保する。

03レイヤー別構成

3.1
Device

シール機側（PIC制御・エッジデバイス）

既存のPICファームウェアに、以下の役割を追加します。既存の制御ロジック（加熱・加圧・冷却シーケンス）自体は変更せず、「測定値の外部送信」だけを追加する形が現実的です。

  • センシング: ヒーター電流（シャント/CT）、ヒーター電圧、シールバー温度（既存の温調用サーミスタを共用可）、加圧ストローク、サイクルタイマー値をADC/タイマーから取得。
  • タイムスタンプ付与とフレーミング: PIC内でリアルタイムクロック（RTCなければサイクル番号で代用）を付け、機体ID・エラーコード・CRC16を含む固定長バイナリフレームに整形。PICのCPU/メモリ負荷を抑えるため、JSONではなく軽量バイナリを推奨。
  • 送信: 既存の通信機能（多くはUART/RS-232系）経由でPCへ1サイクルごと、または一定周期（例: 100ms〜1s）で送信。
ポイント: AIのための改修はPIC側では最小限に。安全機構（サーモスタット、ヒューズ、ソフトウェアの過昇温保護）は現状のまま独立に維持し、AI側の判断ロジックに依存させないこと。

3.1.1PIC18F2550 実装仕様

18F2550は28pin品でオンチップのフルスピードUSBを持つのが特徴です。この特性を踏まえたペリフェラル割り当て案です。

ペリフェラル割り当て
ペリフェラル/ピン割り当て用途
RA0/AN0電流センサー出力（ACS712等ホール式）ヒーター電流監視・寿命トレンド
RA1/AN1シールバー温度（既存サーミスタ流用）温度プロファイル異常検知
RA2/AN2周囲温度環境補正
RA3/AN3加圧ストローク/圧力センサー（任意）機械摩耗トレンド
RC4(D-)/RC5(D+)オンチップUSB（フルスピード・HIDクラス、実装済み）PC直結・PoC標準経路（外部USB-シリアルIC・追加ドライバ不要）
RC6(TX)/RC7(RX) EUSART外付けMAX485経由でRS-485、またはWi-Fiブリッジ複数台バス接続・ネットワーク接続時
OSC1/OSC2外部水晶（例: 20MHz）+ HSPLLUSB使用時は内蔵発振器不可。USB基準クロック生成に必須
Timer0ADCサンプリング割り込み（10〜50ms周期）特徴量計算の元データ取得
Timer1シール/冷却時間の計測（既存ロジック流用）サイクルドリフト検知
EEPROM 256B直近エラーコード・ADC校正値電源断復帰時の状態保持
チップ側の制約と対策:
  • RAMが2KBと小さいため、テレメトリは溜めずに即送信。HID Input Reportにそのまま乗る32〜64byte程度の固定長構造体を1つだけ使い回す。
  • ハードFPUが無く浮動小数点はXC8で高コストになるため、移動平均・簡易RMS推定はQ8.8等の固定小数点演算で実装する。
  • 10bit ADCは電流検出には粗いため、16サンプル程度のオーバーサンプリング平均で実効12bit相当まで分解能を上げる。
  • USB HIDスタック（Microchip MLA の USB Device-HID）はCDCより軽量（Flash消費は概ね3〜6KB程度）で、既に実装済みなら流用がそのまま可能。カスタムHID機器として独自VID/PIDでの列挙になるため、PC側アプリはVID/PIDでフィルタして接続する。
3.2
Transport

通信層

既存の通信機能はUSB-HID（オンチップ、実装済み）とのこと。HIDはWindows標準ドライバで動作するためドライバ配布が不要な反面、仮想COMポートではなくレポート単位のデータ転送になる点が設計に影響します。複数台接続はUSBハブ経由で最大15台をPC1台に集約する方針とします。

通信方式の比較（PIC18F2550・USB-HID前提）
方式特徴適したケース
USB-HID（オンチップ・実装済み）追加ドライバ不要（標準HIDドライバ）。Input Report（例: 64byte、1msポーリング目安）でPCへ送信、Output Reportで簡易な助言通知を受信可能。PC側はシリアルAPIではなくHID API（hidapi等）で読む既存実装をそのまま活用。単機・複数機とも共通の主経路
USBハブ集約（PC直下1段・最大15台）多段カスケードせず、PC直下の1段のみでセルフパワードハブに集約。ポート番号と機体IDを固定対応させやすい。帯域も64byte×15台×10ms間隔≒96KB/sでフルスピード帯域（実効約900KB/s）の1/9程度に留まる1台のPCで複数機を一括監視する構成（本提案の標準形）
EUSART + RS-485/Wi-Fi（参考・任意）PCから離れた棟・フロアをまたぐなど、USBの配線距離（実用上5m前後、延長時はアクティブケーブルが必要）を超える場合の代替USBの配線距離では届かない拠点をまたぐ場合のみ検討

15台規模であればUSB-HID＋ハブ構成のまま帯域・台数上限のどちらにも余裕があるため、RS-485等の追加はPC設置場所からの配線距離がUSBの実用限界を超える場合にのみ検討すれば十分です。

3.3
Gateway

PCエッジゲートウェイ

「リアルタイム性」を担う中心層です。クラウドに依存せず、この1台だけでも監視が完結するように設計します。

  • プロトコル変換: Phase1はUSB HIDレポート（hidapi等のHID APIで受信）、Phase3以降はRS-485/Modbusフレームを受信し、それぞれ正規化したレコードに変換。
  • 時系列蓄積: InfluxDB / TimescaleDB / SQLiteのいずれかにローカル保存（ネットワーク断でもデータを失わない）。
  • 特徴量抽出: 移動平均・移動分散、立ち上がり時間、サイクルタイムのドリフト量などをリアルタイム計算。
  • 軽量推論: しきい値/統計的工程管理（SPC）を最初に実装し、その後Isolation Forestやオートエンコーダ（ONNX Runtime等でエクスポート）へ拡張。
  • ローカル通知: Web UI（Grafana、または自作の軽量ダッシュボード）で現場オペレーターに即時表示。

3.3.1複数台接続（USBハブ・PC直下1段・最大15台）

  • 物理構成: ハブを1段だけPC直下に置き、多段カスケードはしない。具体的には16〜20ポートの産業用セルフパワードハブ1台、または8ポート級ハブ2台をPCの別々のUSBルートポートに接続（この場合も各ハブはPCの直下でありハブ同士のカスケードではないので「1段」）。セルフパワードにするのは、ロジック基板がUSBバス給電の場合にポート供給力（規格上500mA/ポート）を確保するため。
  • ハブの選定（Multi-TT推奨）: ハイスピード対応ハブには内部処理方式にSingle-TTとMulti-TTがある。Single-TTは配下の全フルスピード機器が1つのトランザクション・トランスレータを共有するため、台数が増えるとポーリングの詰まりが出やすい。Multi-TTはポートごとに変換器を持つため、15台をぶら下げても互いの通信が干渉しにくい。今回の転送量（後述）自体は小さいが、余裕を持たせるならMulti-TTハブを選ぶ。
  • ポート↔機体IDの固定マッピング: 1段構成のため「ハブのどの物理ポートに繋いだか」＝「どの機体か」が一意に決まり、多段カスケードのようにポートパスが複雑にならない。設置時にポート番号と機体IDの対応表を1枚作っておけば、現場では「ポート番号を見るだけ」で機体を特定できる。
  • 個体識別（ソフト側）: 全機で同一のVID/PIDになるため、USBディスクリプタのiSerialNumberにEEPROM保持の機体IDを載せて一意化する。PC側はシリアル番号、または上記のポート番号（hid_enumerateで取得できるポートパス）で機体を識別する。
  • ポーリング方式: 起動時に15台分のHIDハンドルをhid_enumerate等で検出してすべてopenしたまま保持し、決められた順序（＝ポート番号順）で1台ずつreadを呼ぶ「順次ポーリング」を採用する。都度open/closeするより抜き差し検出やオーバーヘッドの面で扱いやすい。
  • 帯域の余裕: 64byte Input Reportを10ms間隔で15台分読んでも合計約96KB/s。フルスピードUSBの実効帯域（概ね900KB/s前後）の1/9程度で、1段・単一ハブに集約しても当面はボトルネックにならない。
  • 異常機の扱い: ある機体でread timeoutが連続した場合はスキップして次の機体へ進み、一定回数連続失敗した時点で「オフライン」フラグを立てて通知する（1台の不応答が全体のポーリングを止めない設計）。
3.4
Cloud

クラウド/サーバー層（複数台運用時）

1台のPoCでは必須ではありませんが、複数拠点・複数台に展開する段階で以下を担います。

  • 全機体データの集約・長期保管（時系列DB + オブジェクトストレージ）
  • 異常検知・RUL（残存寿命）モデルの再学習パイプライン
  • 機体間・拠点間の比較分析ダッシュボード
  • 保守ワークオーダーの発行、部品発注システムとの連携
3.5
Action

ダッシュボード・通知

現場向け（今すぐ確認すべきこと）とマネジメント向け（傾向・計画）を分けて設計します。

  • 現場向け: シール機の横に置いたPC画面か、タブレットでの簡易表示。異常は色（緑/黄/赤）と一言メッセージで即座に判別できるように。
  • 管理者向け: メール/Slack/Teams通知＋週次サマリー。ヒーター交換予測日、直近の異常発生履歴などをまとめる。

04AI手法（異常検知・予知保全）

初日から複雑な学習モデルを入れる必要はありません。データが少ない初期は統計的手法で立ち上げ、蓄積量に応じて段階的に高度化するのが実務的です。

Step 1統計的しきい値・SPC

ヒーター電流・温度立ち上がり時間・サイクルタイムそれぞれに対し、正常運転時の平均±nσ（管理限界線）を設定。逸脱をルールベースで即時検知します。導入コストが最も低く、最初の1〜2ヶ月はこれだけでも十分に価値があります。

Step 2教師なし異常検知

複数信号を同時に見たい（電流は正常域だが温度応答だけ遅い、など）場合、Isolation Forestやオートエンコーダ（再構成誤差を異常スコアとする）を導入。ラベル付き故障データが少ない製造現場に適しています。

Step 3予知保全（RUL予測）

ヒーター線（ニクロム線）の抵抗値トレンド、シール時間の緩やかなドリフト、サイクルごとの立ち上がり時間変化などを特徴量とした回帰モデル（勾配ブースティング、またはサイクル系列であればLSTM）で「あと何サイクルで交換が必要か」を推定します。

安全性の原則: どの段階でもAIの出力は「通知・推奨」であり、遮断・停止といった安全動作はPIC側の独立したハード保護（サーモスタット、ヒューズ、既存の過昇温ロジック）に委ねます。AIモデルの誤検知・誤判定が機械の安全機能を代替しない設計とします。

05監視データ項目

まず取得すべき最小限の信号セットです。既存のPIC回路で計測済みの値（温度、タイマー）は流用し、電流センサーなど未実装のものだけを追加します。

06セキュリティと安全性の考え方

  • ネットワーク分離: シール機とPC間のセグメントは工場LAN・社内LANから論理的に分離（VLANなど）。クラウドへの経路のみゲートウェイPCを介して外部接続する。
  • 通信の保護: PC〜クラウド間はTLS。機体認証にはAPIキーまたは機器証明書を用いる。
  • ファームウェア更新: PICのOTA/書き換えを行う場合は署名検証を必須とし、未署名イメージを拒否する。
  • 安全機能の独立性: 前述の通り、AIの判断系と機械安全系（過昇温遮断等）は電気的・論理的に分離し、AI側の障害が安全機能に影響しないようにする。

07導入フェーズ

Phase 0信号の棚卸しとテレメトリ仕様策定〜2週間

現行PICファームウェアで既に取れている値（温度、タイマー）と、追加が必要なセンサー（電流など）を洗い出す。通信フレーム仕様を確定。

Phase 1PoC: 1台構成でのデータ収集・しきい値監視1〜2ヶ月

シール機1台＋PC1台で通信を確立し、時系列DBへの蓄積とSPCベースのアラートを立ち上げる。

Phase 2機械学習による異常検知の導入2〜3ヶ月

蓄積データを用いてIsolation Forest/オートエンコーダを学習。ローカルダッシュボードで異常スコアを可視化。

Phase 3複数台展開とクラウド集約、RUL予測3〜6ヶ月

USBハブ経由で最大15台をPC1台に集約、クラウドに集約。ヒーター寿命などの残存寿命予測モデルを追加。

Phase 4保守ワークフローへの統合継続運用

アラート発生時に保守指示・部品発注まで連携するワークフローを構築し、運用を定着させる。

08構成の代替案

PC1台にどこまで持たせるか、クラウドにどこまで任せるかはトレードオフです。導入初期の規模感に応じて選んでください。

エッジ重視構成（推奨・初期）

  • 判定はほぼPC上で完結、レイテンシが小さい
  • ネットワーク断でも監視が継続する
  • クラウド利用料が小さく、初期コストを抑えられる
  • 複数拠点の横断分析はしづらい

クラウド重視構成（拡張期）

  • 複数台・複数拠点のデータを一元管理できる
  • モデルの再学習・展開を中央で統制できる
  • ネットワーク依存が大きく、通信断時のフォールバックが必要
  • 台数が増えるほどコスト効率が良くなる
